### 体言止め対応の具体例（ユーザーが問題視した要約）

- 不合格（旧要約）:
  ```text
  米マイクロソフトが深刻なアラートを出し、
  障害の防止や対応の仕組みを見直すことにしました。
  復旧を１時間以内に終える目標も掲げました。
  ```
  → 何のアラートか／理由／障害内容が分からない。

- キーワードは改善したが体言止めが残った版:
  ```text
  米マイクロソフトがコードレッドを宣言
  世界的な大規模障害を受けて
  復旧を1時間以内に終える目標   ← 体言止め
  ```

- 修正後のルール: 各行を述語で終える。例:
  ```text
  米マイクロソフトがコードレッドを宣言しました
  世界的な大規模障害を受けています
  復旧を1時間以内に終えるとしています
  ```

機械的な保険として `src/text_quality.py::has_taigen_dome()` を `src/ai_client.py`（要約検証時）と `src/notifier.py`（送信前）の両方で呼ぶ。検出時は再生成／通知しない（フェイルクローズ）。

## 2. 技術選定・構成の判断

| 判断 | 採用内容 | 理由 |
|---|---|---|
| 処理の主役 | Python（RSS取得・順序制御・DB・エラー処理・通知） | ショートカット単体では順序・履歴・再試行が困难的ため（設計書 2-2） |
| AI呼び出し | macOSショートカット `News_Summarize` / `News_Review` 経由の Apple Intelligence | 有料APIを使わないため |
| プロンプ置き場 | Python側 `config/prompts/*.txt` が唯一の管理元 | ショートカットを汎用パススルー（入力テキスト→「モデルを使用」→出力）にしたため、プロンプト変更時にショートカット再生成が不要 |
| 修正要約 | 専用ショートカットを作らず `News_Summarize` に `revise.txt` を渡す | 登録ショートカットを2つのままにするため |
| レビュー | 同一モデルに別役割プロンプトを与える構成 | 実機で複数モデルの選択が確認できなかったため。完全独立検証ではないことを認識済み |
| 自動実行 | launchd ユーザーエージェント `~/Library/LaunchAgents/com.aki.news-telegram.plist`、5分間隔 | `shortcuts` CLI は GUI ユーザセッションが必要。サンドボックス内からは動作しない実測結果に基づく |
| 多重起動対策 | `fcntl.flock`（`data/news.lock`）で非ブロッキング排他 | AI呼び出しが要約約97秒／レビュー約193秒で5分間隔と衝突するため |
| 同時処理数 | `max_articles_per_run: 1` | 上記処理時間の実測を反映（初期値5から変更） |
| DB | SQLite（WALモード）、記事キーは GUID→正規化URL→URL+見出しハッシュ | 冪等性と状態履歴の記録のため |
| HTTP | `httpx` で `follow_redirects=True` | Yahoo!ニュースの302リダイレクトで本文取得が失敗した実バグを修正 |

## 3. 通知仕様の判断（実機検証で確定）

| 項目 | 設計書の初期値 | 実装で採用した値 | 理由 |
|---|---|---|---|
| 行数 | 4行以内 | **3行以内** | iPhone通知センターでの見え方を実機確認 |
| 文字数 | 50〜65文字目安 | **35〜55文字**（55文字超は拒否） | 65文字＋URLでは省略されたため |
| URL | 本文末尾にURL文字列 | **本文に入れず Telegram `text_link` entity** で「元記事を読む」に付与 | 表示文字数を削り、通知プレビューで要約が省略されないようにするため |
| 開いた後 | 要約全文＋リンク | 同上（全文は55文字以内、リンクはタップ可能） | 設計書 8-2 / 19 を満たす |

`Telegram` の `offset` / `length` は **UTF-16コード単位** で指定する（`src/notifier.py::_utf16_len()`）。

## 4. 要約に必須の情報（6要素）

ユーザー指摘「何に対してのアラートなのか、なんでアラートを出したのか、何の障害なのか、どんな対応、なんで対応するのか」を結構化したもの。記事に明記がある場合のみ含める（推測禁止）。

1. **主体**（固有名詞をそのまま。例: 米マイクロソフト）
2. **出来事名**（例: コードレッド、世界的な大規模障害）
3. **対象**（何に対してのアラート／対応か）
4. **理由**（「〜を受けて」など記事明記の事情）
5. **対応**（数値目標を含む）
6. **目的**（記事に明記がある場合のみ）

これらを `summarize.txt` / `revise.txt` に必須化し、`review.txt` では欠落を不合格基準にしている。一般的な言い換え（「深刻なアラート」「仕組みを見直す」）だけも不合格。
