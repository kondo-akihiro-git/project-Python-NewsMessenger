### 体言止め対応の具体例（ユーザーが問題視した要約）

- 不合格（旧要約）:
  ```text
  米マイクロソフトが深刻なアラートを出し、
  障害の防止や対応の仕組みを見直すことにしました。
  復旧を１時間以内に終える目標も掲げました。
  ```
  → 何のアラートか／理由／障害内容が分からない。

- キーワードは改善したが体言止めが残った版:
  ```text
  米マイクロソフトがコードレッドを宣言
  世界的な大規模障害を受けて
  復旧を1時間以内に終える目標   ← 体言止め
  ```

- 修正後のルール: 各行を述語で終える。例:
  ```text
  米マイクロソフトがコードレッドを宣言しました
  世界的な大規模障害を受けています
  復旧を1時間以内に終えるとしています
  ```

機械的な保険として `src/text_quality.py::has_taigen_dome()` を `src/ai_client.py`（要約検証時）と `src/notifier.py`（送信前）の両方で呼ぶ。検出時は再生成／通知しない（フェイルクローズ）。

| 同時処理数 | `max_articles_per_run: 1` | 上記処理時間の実測を反映（初期値5から変更） |
| DB | SQLite（WALモード）、記事キーは GUID→正規化URL→URL+見出しハッシュ | 冪等性と状態履歴の記録のため |

| AI出力の揺れ | 不完全JSONを厳密検査で弾き、必要な場合のみ安全に復旧／再試行 | 実機で `summary` 直後の切り上げ・日本語鉤括弧・文字数超過を観測。復旧時も事実は補わず、レビューと体言止めガードを維持するため通知の安全性は落とさない |

## 4. 要約に必須の情報（6要素）

ユーザー指摘「何に対してのアラートなのか、なんでアラートを出したのか、何の障害なのか、どんな対応、なんで対応するのか」を結構化したもの。記事に明記がある場合のみ含める（推測禁止）。

1. **主体**（固有名詞をそのまま。例: 米マイクロソフト）
2. **出来事名**（例: コードレッド、世界的な大規模障害）
3. **対象**（何に対してのアラート／対応か）
4. **理由**（「〜を受けて」など記事明記の事情）
5. **対応**（数値目標を含む）
6. **目的**（記事に明記がある場合のみ）

これらを `summarize.txt` / `revise.txt` に必須化し、`review.txt` では欠落を不合格基準にしている。一般的な言い換え（「深刻なアラート」「仕組みを見直す」）だけも不合格。

さらに **4W1H** を重ねる（2026-11-26）:

- WHO: 固有名詞の主体。役職だけ（「総務相」）は不可で、氏名を添える（「藤井総務相」）。
- WHAT: 具体的な出来事名。「原因究明を求めました」だけでは不可で、何の原因／何への対応かを同じ文に書く。
- WHEN / WHERE: 記事に明記があれば残す。
- WHY / HOW: 6要素の理由／対応に相当する。目的は記事に明記がある場合のみ。

## 5-1. 判断: Cloud 障害時のオンデバイス切替と誤承認への機械ガード（2026-11-26）

- **状況**: Shortcuts Cloud モデルが15時間以上 `現在、リクエストを完了できません。` を返し続けた。新規作成ショートカットでも同じで、SHORTCUTS／コード側の不具合ではない。
- **ユーザー判断**: 管理者権限で Command Line Tools for Xcode 27.2 を導入し、オンデバイス推論へ切替える。有料AI APIへのフォールバックは絶対に行わない。
- **ガイド付き生成**: オンデバイスモデルは自由形式JSONを崩しやすいため、`llm.json()` と `SUMMARY_SCHEMA` / `REVIEW_SCHEMA` でキーと型を固定。キー欠けは型だけ補完し、事実は追加しない。
- **誤レビューへの対応**: オンデバイスモデルが19文字の要約に「6要素あり」と PASS を出したため、AI判断に依存せず機械ガードを追加。
  - `trim_related_articles()`: 関連記事一覧を本文から除去（別記事の事実混入防止）。
  - `missing_required_elements()`: 最低35文字未満、または見出しの固有語が1つも無い場合は通知しない。
  - 理由／目的は記事に明記がない場合もあるため、機械ガードでは判定せず AI レビューに委ねる（强行注入を避ける）。
  - `config/prompts/shorten.txt` に「35文字未満にしない」と明記。
- **判断の優先順位**: 通知件数より正確性を優先する。条件を満たさない記事は `INSUFFICIENT_CONTENT` として通知しない（フェイルクローズ）。
- **結果**: 76件PASS、実RSS記事で承認→Telegram送信成功（51文字・述語終わり）、弱い要約は拒否。launchd は再試験後に再有効化済み。

## 5-3. 判断: 2行・4W1H・単一イベント・根拠なき評価の禁止（2026-11-26）

- **ユーザー指摘**: 通知済みの `NTTドコモへの信頼が揺らぎつつあります。藤井総務省が原因究明をもとめました。` は、背景イベントが無い評価、WHO/WHATの欠落、複数イベントの混入があった。
- **仕様**: 要約は55文字以内・最大2行。1行目に主要ニュース、2行目は補足のみ。記事に2つのイベントがあっても主要イベント1つに絞る。6要素に加えて4W1Hを必須とし、根拠のない評価表現は背景イベントと根拠が要約内に無ければ不合格。
- **再現試験で判明したAI誤承認**:
  1. `NTTドコモは11月5日、11日、16日に5G SAで通信障害が発生しました。総務相は原因究明を求めました。` → 5G SA未説明・氏名なし。
  2. `11月5日、11日、16日にNTTドコモで3度の通信障害が発生しました。藤井総務相が原因究明を求めました。` → 氏名はあるが独立した2イベント。「何の原因か」も同じ文に無い。
- **判断**: AIレビューが PASS を返しても信頼しない。`concrete_basis_ok` / `four_w_one_h_ok` / `single_event_ok` / `missing_4w1h` をスキーマ化し、false や不足配列があれば `validate_review_payload()` が FAIL へ上書きする。さらに `text_quality.py` で、根拠なき評価・同一文に無いWHO/WHAT・初見用語未説明・役職のみ・複数イベントを機械拒否する。
- **行数の扱い**: 最大2行。改行は1文の途中でもよいが、行末は必ず述語で終える（体言止め禁止は維持）。
- **結果**: `pytest -q tests/` は94件PASS。`main.py --check-only` OK。再現試験の最終状態は `PROGRESS.md` を参照。
- **運用**: 品質を保証できない記事は `SUMMARY_FAILED` / `REVIEW_REJECTED` とし、絶対に通知しない。件数より正確性を優先する方針は不変。

## 5-1. 品質不合格時は再生成・再レビューを継続（2026-11-27）

- **ユーザー指摘**: 「基準を満たす要約が出ないことで通知件数が減ることはない」認識。基準を満たさない場合は再要約→再レビューを繰り返し、RSS更新件数と通知件数は合致するはず、という期待。
- **判断**: 認識は概ね正しいが、例外がある。正確性最優先・フェイルクローズのルール（本文不足、AI利用制限／タイムアウト、送信失敗）は維持し、これら外部障害では通知しない。品質基準そのものが理由で通知を減らすことはしない。
- **実装**:
  - `SummaryQualityError` で品質不合格を区別し、AI障害と異なるループへ送る。
  - 要約検証時に見出しの固有語・最低文字数も確認し、AI内の再試行で解消する。
  - 修正要約も品質ガード抵触時は再生成を続け、基準を満たしたものだけを再レビューする。
  - 安全上限 `max_summary_attempts` / `max_revision_attempts`（既定60）を設け、無限ループを防ぐ。上限到達時のみ手動確認対象として通知しない。
- **実試験で判明した調整**: 初見用語の再生成では、説明を足すより略語回避を明示した方が55文字制限と両立する。またプロンプト強化分が4096トークン窓を超過したため、AI渡し本文を450→350文字へ短縮した（要約プロンプト約2986文字）。
- **機械圧縮の上限**: 55文字超過の安全策は「しました」→「した」のような自然なサ変述語の言い換えだけに限定する。「ました」→「した」は「発生しした」等の不自然な述語を生むため禁止し、不自然な述語は見出し未渡しでも品質不合格とする。
- **結果**: 単体テストで「品質不合格2回→承認」と「AI障害は即停止」を確認。`pytest -q tests/` は102件PASS。実記事では3回の再生成後に承認要約（40文字・1行）を実送信し、RSS更新1件／通知1件の一致を確認。

## 5-2. RSS更新件数との照合・文字数ループ・RSS追加・法人格表記（2026-11-27）

- **ユーザー確認依頼**: 当日の通知が5件しかないが、RSS更新件数と一致しているか確認してほしい。少ないならプロンプトを調整してほしい。

- **判断**: 文字数超過はAIが同じ文を繰り返しがちなため、意味を変えない定型表現（`〜について議論`→`〜を議論`、`〜に対して`→`〜に`、`発生しました`→`発生した`）だけを機械的に短縮して全ガードを再検証する。不自然な述語を作る置換（`ました`→`した`）は禁止を維持。あわせて成功例をfew-shotでプロンプトへ追加。
- **RSS追加**: 公式RSSが当日更新されている GIGAZINE と PC Watch を追加。404／到達不可の CNET Japan、Publickey、マイナビニュース、Engadget Japanese と、配信が古い NHK は採用しない。
- **法人格表記**: ユーザー要望は「はっきり会社を指せる場合だけ前株／後株を付ける」。本文・見出しに明記された正式名称だけを使い、推測で `(株)` / `株式会社` を付けない。根拠のない法人格は `SummaryQualityError` で機械拒否する。
- **情報の集約**: ユーザー質問・回答・認識の履歴を `docs/USER_QA.md` に集約し、`AGENTS.md` / `README.md` から参照する。どのAIエージェントからも同じ現状が把握できるようにする。
