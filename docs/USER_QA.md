# USER_QA.md — ユーザー質問・回答・認識の履歴

このファイルは、ユーザーから受けた質問・指摘と、それに対する回答／判断／実装状況を時系列で記録したものです。
どのAIエージェント・どのPCから作業を再開しても、まず `AGENTS.md` とこのファイルを読めば現状と開発方針が把握できるようにします。

最終更新: 2026-11-27

---

## 1. 現在できていること（要約）

- RSS取得（Yahoo!ニュース ITトピックス／Yahoo!ニュース ITmedia配信／ITmedia NEWS／GIGAZINE／PC Watch）→ 記事本文取得 → オンデバイス Apple Intelligence 要約 → AIレビュー → Telegram通知、まで一貫して動作。
- 通知本文は **要約のみ**。URL・リンク文言・`text_link` entity は付けない。
- 要約は **1行・35〜60文字**（iPhone通知で3行以内）。改行なし。1行目に主要ニュース。日付・時刻は含めない。明らかな会社名には記事に明記された法人格（株式会社／(株)）を正しい位置で付ける。
- 品質基準: 6要素・4W1H・単一イベント・初見用語の説明・述語終わり・根拠なき評価の禁止。
- 品質基準に抵触した要約は、基準を満たすまで再生成・再レビューを繰り返す。
- AI利用制限・タイムアウト・本文不足・送信失敗などの外部障害のみ即フェイルクローズ。有料AI APIへはフォールバックしない。
- 法人格表記（株式会社／(株)）は、記事本文または見出しに明記がある場合だけ使用し、推測で付けない。
- `launchd` により5分間隔で自動実行（排他ロック付き）。DB・ログ・`.env` はGit管理外。

## 2. 開発方針（現在の認識）

1. **正確性最優先**: 記事本文にない事実・理由・目的は絶対に追加しない。
2. **通知件数より品質**: ただし「品質基準を満たさないこと」を理由に通知を減らさない。基準を満たすまで再生成する。
3. **外部障害は通知しない**: AIが使えない、本文が足りない、送信に失敗した場合は通知しない。
4. **証拠を残す**: 判断・設計差分・実機検証結果は必ず `.md` に記録し、Gitへpushする。

## 3. 質問と回答の履歴

### 2026-11-26: 通知からリンクを外してほしい

- **ユーザー質問/指示**: 通知に「元記事を読む」などのリンクやURLを付けないでほしい。
- **回答/対応**: `src/notifier.py` を変更し、要約文章のみを送信。`text_link` entity も廃止。設計書原本にリンク付き形式の記載があっても、ユーザー指示を優先する（`docs/DECISIONS.md` に記録済み）。
- **状態**: 完了。

### 2026-11-26: 低品質通知（NTTドコモ／藤井総務省）の再発防止

- **ユーザー指摘**: `NTTドコモへの信頼が揺らぎつつあります。藤井総務省が原因究明をもとめました。` は、背景のない評価、WHO/WHATの欠落、誤役職を含んでおり不合格。
- **回答/対応**: 55文字以内・最大2行・1主要イベント・4W1H・初見用語説明・述語終わりをプロンプトと機械ガードの両方へ実装。AIがPASSを返しても `concrete_basis_ok` / `four_w_one_h_ok` / `single_event_ok` が false なら FAIL へ上書き。
- **実検証**: 対象記事を再現試験し、`藤井総務相がNTTドコモの「5G専用設備」による通信障害の原因究明を求めました。`（40文字・1行）を承認・実送信。
- **状態**: 完了。

### 2026-11-27: 品質基準で通知が減るのはおかしい

- **ユーザー認識**: 基準を満たさない要約は再生成・再レビューを繰り返すため、最終的にRSS更新件数と通知件数は一致するはず。
- **回答**: 概ね正しい。ただし例外として、本文不足・AI利用制限／タイムアウト・ブリッジ失敗・送信失敗などの外部障害では従来どおり通知しない。品質基準そのものを理由に通知を減らすことはしない。
- **対応**: `SummaryQualityError`（品質不合格＝再生成対象）と外部の `AIClientError`（即フェイルクローズ）を区別。安全上限 `max_summary_attempts` / `max_revision_attempts`（既定60）を追加。
- **状態**: 完了。

### 2026-11-27: 今日の通知が5件しかない。RSS更新件数と一致しているか確認してほしい

- **ユーザー質問**: Yahoo!ニュースとITmedia NEWSのRSS更新が5件しかないのは少ないように思える。一致していれば現状精度でよく、少ないならプロンプトを調整してほしい。
- **確認結果（2026-11-27 JST）**:
  - 質問時点の通知は5件だったが、確認時点では **8件** に増えていた（`launchd` が動作中）。
  - DB上の当日RSS新着は **18件**（Yahoo ITmedia配信10、ITmedia NEWS6、Yahoo ITトピックス2）。
  - つまり **8件 < 18件** で、やはり差分がある。
  - 失敗10件のうち8件は要約生成失敗、その原因は **すべて55文字超過**（57〜109文字）。本文不足は2件のみ。
- **回答/対応**: 文字数超過のループを断つため、以下を実装。
  - 意味を変えない定型表現だけを機械的に短縮（`発生しました`→`発生した`、`〜について議論`→`〜を議論`、`〜に対して`→`〜に`）。不自然な述語（`発生しした` 等）は作らない。
  - 再生成プロンプトへ55文字の成功例（実承認済み要約）をfew-shotで追加。
  - レビューでは細部の省略を許容し、6要素・4W1H・初見用語説明・主要ニュースだけを厳格判定する既存方針を維持。
- **状態**: 完了。実記事 `飲食店の“AI商品画像”は景品表示法違反にならないの？` で `飲食店が生成AIで生成した画像が景品表示法違反にならないと専門家が指摘しました。`（36文字）がレビューPASS・実Telegram送信成功（`PROGRESS.md` に記録）。

### 2026-11-27（続き）: 別記事の内容が要約に混ざる問題

- **判明した事実**: 実試験の失敗要約2行目に、全く別の記事の「藤井総務相が原因究明を求めました」「5G SAという5G専用設備」が繰り返し混入した。
- **原因**: 文字数の成功例としてプロンプトへ埋め込んだ**実記事の要約例**を、オンデバイスAIが現在の記事の事実としてコピーしていた。
- **回答/対応**: 4つのプロンプトから実名・実出来事の例をすべて撤去し、架空の書式プレースホルダ（「〈用語〉という〈記事に書かれた意味〉」）と「例文のコピー禁止」ルールへ置換。テストで実名例の再混入を検出するようにした。
- **追加対応**: AIが改行せず「。」で2文目を繋ぐため、文境界を行境界として扱い、55文字超過時に1行目だけで全品質ガードを満たせるなら補足文を落とす処理を追加。6要素・4W1Hの最終判定は従来どおりAIレビューが担う。
- **状態**: 完了。109件PASS、実記事で混入なし・承認・通知成功。旧 `SUMMARY_FAILED` 8件も再処理で解消。新RSS2フィード追加で当日新着は74件、11/27の実通知は11件。残りは未処理（AIが1件ずつ順次処理）または本文・品質ガード不足で、フェイルクローズ方針は維持。

### 2026-11-27（続き）: 自動実行の競合

- **対応**: 競合プロセスを停止し、ジョブを `bootout` + `disable`。検証完了後に `enable` して戻す。
- **状態**: 完了。`launchctl enable` + `bootstrap` + `kickstart` で自動実行を再有効化し、`enabled` / `state = running` を確認済み（5分間隔）。

### 2026-11-27: 会社名には前株/後株を付けてほしい（分かる場合のみ）

- **ユーザー質問**: 会社について発表しているニュースで、はっきり会社を指していることが分かるなら「(株)」のような法人格を付けてもらえるとわかりやすい。ただしすべての会社名に付けてほしいわけではない。
- **回答/方針**: 前株（株式会社X）か後株（X株式会社）かは **記事本文の表記だけを根拠に判断** する。本文に正式名称が明記されている場合はその表記をそのまま使う。本文に法人格の表記が無い場合は通称のままで、`(株)` や `株式会社` を推測して付けない。
- **対応**: `summarize.txt` / `revise.txt` / `shorten.txt` / `review.txt` に方針を明記。`src/ai_client.py` に、本文・見出しに根拠がない法人格表記を机械拒否するガードを追加。
- **状態**: 完了（単体テストで展開）。
